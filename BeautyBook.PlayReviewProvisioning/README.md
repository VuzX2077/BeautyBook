# Play Review provisioning CLI

Developer-operated maintenance tool. It does not start the web host, hosted workers,
PayOS, Brevo or Expo. No migrations are created or applied by this tool.

## Commands

Run from the repository root. Build once before the maintenance window.

```powershell
dotnet run --no-build --project BeautyBook.PlayReviewProvisioning -- validate --config <local-json> --expect-env <environment> --expect-host <host> --expect-db <database>
dotnet run --no-build --project BeautyBook.PlayReviewProvisioning -- provision --config <local-json> --expect-env <environment> --expect-host <host> --expect-db <database> --assets <local-directory>
dotnet run --no-build --project BeautyBook.PlayReviewProvisioning -- provision --config <local-json> --expect-env <environment> --expect-host <host> --expect-db <database> --assets <local-directory> --apply --maintenance-ack STOPPED_AND_DRAINED
dotnet run --no-build --project BeautyBook.PlayReviewProvisioning -- refresh-scenarios --config <local-json> --expect-env <environment> --expect-host <host> --expect-db <database> --assets <local-directory> --apply --maintenance-ack STOPPED_AND_DRAINED
dotnet run --no-build --project BeautyBook.PlayReviewProvisioning -- rotate-credential --config <local-json> --expect-env <environment> --expect-host <host> --expect-db <database> --apply --maintenance-ack STOPPED_AND_DRAINED
```

Without `--apply`, provision/refresh/rotate are dry runs: no DB/storage writes or
password input. `validate` checks an already-provisioned graph and downloads private
media to verify its checksum; it never uploads, signs URLs, writes or asks for a
password. Validation fails on an empty database; initial provision dry run reports
that resources would be created. Exit 0 is success, 2 is a controlled failure.

## Secrets and target

Supply `BBOOK_ConnectionStrings__Provisioning` and storage credentials through the
operator's secret-injection environment, never through arguments or tracked files.
Do not type literal secrets into shell history. Storage variables:

```text
BBOOK_Supabase__Url
BBOOK_Supabase__ServiceRoleKey
BBOOK_Supabase__VerificationBucket
BBOOK_Supabase__StorageBucket
```

Private bucket must already exist and be private, distinct from the public bucket.
The public bucket is only for sample avatars/portfolio. Do not send identity images
there. Supabase adapters validate private bucket state on upload/read.

Reviewer password is requested with hidden interactive input only on account
creation or explicit credential rotation (12–128 characters). Redirected stdin is
rejected. It is never included in results, manifests, logs or errors. Counterpart
has a null password hash. Successful provision reruns never rotate credentials.
There is no persisted manifest/report generated by the CLI: results are fixed,
non-secret status messages. The backend's existing hashing algorithm is reused.

## Local config (outside Git)

Provide these non-secret values in JSON; property names are case-insensitive and
unknown properties are rejected:

```text
EnvironmentName
ReviewUserId, CounterpartUserId, SampleBankAccountId (distinct nonempty GUIDs)
ReviewEmail, CounterpartEmail (distinct, normalized, not existing real accounts)
BookingTimeZoneId (same value as backend Booking:TimeZoneId)
BankCode, BankBin (a matching known source mapping; default VCB/970436)
City is derived from the selected operating province, not entered separately.
OperatingProvinceCode, OperatingAreaId (valid pair in embedded OperatingAreas catalog)
Latitude, Longitude (public/business sample meeting point, never home coordinates)
LocationLabel (clearly sample)
AssetsDirectory
SampleAssetsAcknowledged=true
AssetFiles (purpose-to-local-filename dictionary)
AssetChecksums (optional purpose-to-original-file-SHA256 dictionary)
```

Expected environment/host/database come separately from the required CLI arguments.
Host/database are exact matches to the connection string. A mismatch, missing IDs,
missing maintenance acknowledgement or unknown bank mapping aborts before writes.
Use a single PostgreSQL host (no host list). Configuration is not runtime demo
authority; runtime still uses the four Phase 3 PlayReview keys.

## Operator assets

Eight purposes are required, each mapped to a filename inside the supplied directory:

```text
identity-front, identity-back, portrait
review-avatar, counterpart-avatar
portfolio-1, portfolio-2, portfolio-3
```

JPEG, PNG or WebP, at most 10 MB, at most 24 megapixels, minimum 320×240 pixels.
Decoded content is validated and re-encoded using existing VerificationImage, with
EXIF/GPS removed. Extension, existing regular file, purpose mapping and configured
SHA256 are checked. No URLs, traversal or symlink asset files; no arbitrary fetch.

Front/back must be non-government sample cards, never real ID scans or a close copy
of a real CCCD. No real emblem, identity number, barcode, QR or personal information.
The tool adds a large `SAMPLE / NOT A REAL ID / FOR APP REVIEW` watermark. Portrait
should be an illustration. Operator acknowledgement is necessary because software
image validation cannot determine whether pixels contain a real person's document.
Do not commit operator media binaries. Tests generate their own synthetic images.

## Maintenance and lifecycle

Before any apply: stop/drain application traffic and background writers; keep it
stopped until post-apply validation passes. `STOPPED_AND_DRAINED` is an explicit
operator attestation, not an automatic session detector. Simulation disabled alone
does not prove that requests or sessions are idle. No login/logout reset exists.

Pair-specific PostgreSQL session advisory lock rejects a concurrent tool with
`PROVISIONING_BUSY`. User row locks protect each database transaction. Initial
foundation, media attach and scenario graphs use separate transactions: DB and
storage cannot be atomic together. A failed upload may leave only tracked private
media with no Ready/Attached; a crash after upload is recovered by checksum read.
An uploaded resource whose attachment rolled back remains tracked for maintenance
cleanup. Successful reruns don't upload duplicate linked media. Foundation may remain
after a later stage fails; simulation must remain disabled until complete validation.

Existing normal accounts are never adopted, including apparently empty ones. Email
collisions, non-Draft profiles, real banks/identity/history, mixed domains, unknown
owner-linked activity and inconsistent financial graphs abort. This conservative
tool may reject unrelated demo activity such as reviews/chat; it never deletes that
activity to force a reset. Fix unexpected state by investigation, not blanket deletion.

Seven scenario keys have deterministic IDs under the configured pair. Provision
creates generation 0 and doesn't restore consumed states. Refresh appends only when
an interactive scenario was consumed/stale: incoming appointment < now+7 days,
customer confirmation deadline elapsed, old InProgress, or no available earnings.
Completed refund/payout history is not recreated every run. History is preserved.
Slot allocation avoids all existing same-MUA appointments; old slots never move.
Multiple generations can increase the list size; no automatic pruning is implemented.

One UTC reference time is used for scenario creation. Business dates use the backend
timezone, not the host's timezone. Incoming appointments are approximately +30/+31
days; historical appointments -1/-2/-4 days. WaitingCustomer records a recent sample
completion submission and a 24-hour confirmation deadline. Demo workers do not make
these samples evergreen: validate freshness before each review round and refresh
only in an enforced maintenance window.

## Activation (operator instructions only)

Keep runtime SimulationEnabled=false. Deploy reviewed backend/tool as appropriate;
stop/drain traffic; check expected target and assets; run provision dry run; apply;
run validate; set the already-chosen three runtime IDs and enable simulation only
after graph and frontend review are complete; resume traffic; smoke-test login and
both modes without real providers. Supply the exact credential in Play Console.
Do not log the credential. On later review rounds, use refresh rather than resetting
old states. Credential rotation is a separate maintenance operation and requires
updating Play Console. These steps are not executed by the implementation task.
